    Section 1 of 12

    What is version control and why use it?

    Every software project changes constantly. Version control gives you a reliable record of those changes, so you can experiment safely, recover earlier work and show how your project developed.

    In this section you will

    • explain what version control is;
    • describe why version control is useful for your own projects.

    Key term

    Version control is a system that records changes to a set of files over time. It lets you see what changed, when it changed and why, and it lets you return to any earlier version.

    The problem version control solves

    Without version control, most people keep versions by copying and renaming files. This quickly becomes confusing, and it is easy to lose work or overwrite the wrong copy.

    Each point in the history on the right is a saved snapshot of the whole project, with a short message explaining what changed. You only ever work in one folder, and you can return to any earlier point.

    Worked example: looking back through history

    Sam is building a portfolio website. Move the slider to view the file index.html at each point in its history. Lines highlighted with a green bar were added in that version, and lines with a blue bar were changed.

    Version 1Version 2Version 3Version 4

    Notice version 2 contains a spelling mistake in the link (abot.html). Because every version is recorded, Sam can see exactly when the mistake appeared and when it was fixed. If a later change broke the page, Sam could compare versions or restore an earlier one.

    Why use version control?

    • Undo mistakesReturn a file, or the whole project, to a version that worked.
    • A complete historySee what changed, when and why, for every file.
    • An off-site backupOnce your work is on GitHub, losing your laptop does not mean losing your project.
    • Safe experimentsTry new ideas separately and only keep them if they work.
    • CollaborationSeveral people can work on the same project without overwriting each other.
    • Evidence of your processA steady history shows tutors and employers how you developed your work.

    Version control is used in almost every software company. Learning it now is one of the most useful professional skills you can develop on your course.

    Your prediction

    The answer is none of it. Git stores snapshots in a hidden folder inside the project on your own computer. Until you send them to an online service such as GitHub, no other copy exists. The next section explains this difference between Git and GitHub.

    Section 2 of 12

    Git versus GitHub

    Git and GitHub are often mentioned together, but they are different things. Git works on your computer. GitHub is a website that stores a copy of your work online.

    In this section you will

    • explain the difference between Git and GitHub;
    • describe the difference between a local repository and a remote repository.

    Key terms

    Git
    Free version control software that runs on your own computer. It records the history of your project in a hidden folder called .git inside your project folder. Git works without an internet connection.
    GitHub
    A website and online service that stores Git projects on the internet, so that you can back them up, share them and work with others.
    Repository (often shortened to "repo")
    A project folder whose history is tracked by Git. It contains your files and the complete record of every saved change.

    Local and remote repositories

    When you use Git and GitHub together, there are two copies of your repository.

    Local repository

    On your computer. You work on it in VS Code, and Git records its history.

    Push →send your work up to GitHub
    ← Pullbring new work down from GitHub

    Remote repository

    On GitHub. You view and manage it in your web browser.

    Key terms

    A local repository is the copy of a repository on your own computer. A remote repository is a copy stored on a server, such as GitHub. VS Code gives your GitHub remote the name origin by default.

    An analogy

    Think of Git as the camera on your phone: it takes photos (snapshots of your project) and keeps them in the phone's album. GitHub is an online photo library that you choose to upload the album to. If you lose your phone, the uploaded photos are safe, but only the ones you actually uploaded.

    Other services, such as GitLab and Bitbucket, do the same job as GitHub. The Git skills in this resource transfer directly to them.

    Setting up

    Before you start, you need a GitHub account, Git installed on your computer and VS Code signed in to GitHub. You only need to do this once on each computer you use.

    In this section you will

    • create a GitHub account;
    • install Git and tell it who you are;
    • sign in to GitHub from VS Code.

    Using a university computer?

    Git and VS Code are usually already installed on university computers. You will still need your own GitHub account, and you may need to complete steps 3 and 4 each time you use a different computer.

    1Create a GitHub account

    1. Go to github.com and select Sign up.
    2. Use an email address you will keep after your course ends. You can add your university email address later in Settings > Emails.
    3. Choose a professional username, because employers may see it. For example, sam-taylor-dev is better than xXgamerXx.
    4. Turn on two-factor authentication when GitHub asks you to. GitHub requires it for accounts that contribute code.
    5. Optional: apply for GitHub Education using your university email address to receive free benefits for students.

    2Install Git

    • Windows: download Git for Windows from git-scm.com and run the installer, accepting the default options.
    • macOS: when you first use Git features, VS Code will prompt you to install the Xcode Command Line Tools, which include Git. You can also download Git from git-scm.com.
    • Linux: install the git package using your distribution's package manager.

    Restart VS Code after installing. Open the Source Control panel: if Git is installed, you will no longer see a message asking you to download it.

    3Tell Git who you are (one time only)

    Git labels every commit with your name and email address. VS Code does not have a settings screen for this, so this is the only step in this resource that uses the terminal. In VS Code, select Terminal > New Terminal, type each command below with your own details and press Enter after each one.

    $ git config --global user.name "Sam Taylor"$ git config --global user.email "sam@example.com"

    Use the email address linked to your GitHub account, so that your commits appear on your GitHub profile. To keep your address private, use the "noreply" address shown in GitHub under Settings > Emails.

    Common mistake: skipping this step

    If you skip it, VS Code shows a message asking you to configure your user.name and user.email the first time you try to commit, and the commit will not be made.

    4Sign in to GitHub from VS Code

    VS Code needs permission to send work to your GitHub account. Select the Accounts icon at the bottom of the Activity Bar (the strip of icons on the far left) and choose Sign in with GitHub. VS Code opens your browser so that you can authorise it. VS Code may also ask you to sign in automatically the first time you clone or push.

      Section 5 of 12

      The core workflow: changes, staging, committing, pushing and pulling

      This is the routine you will repeat every time you work on a project. Once you understand the four areas where your work can be, every Git action makes sense.

      In this section you will

      • describe the four areas: working directory, staging area, local repository and remote repository;
      • use the Source Control panel to stage, commit, push and pull;
      • recognise the Git command behind each action.

      Key terms

      Working directory
      Your project folder as it is right now, including edits you have saved but not yet committed.
      Staging area
      A holding area for the changes you have chosen to include in your next commit. Adding a change to it is called staging.
      Commit
      A saved snapshot of your staged changes, stored in your local repository with a message, your name, the date and a unique ID called a hash.
      Push
      To send your new commits from your local repository to the remote repository on GitHub.
      Pull
      To bring new commits from GitHub into your local repository and update your files.

      The four areas

      1. Working directory. You edit and save index.html. VS Code lists it under Changes with the letter M (modified). New files show U (untracked).
      2. Staging area. You select + next to the file. It moves to Staged Changes, ready to be committed.
      3. Local repository. You type a message and select Commit. The snapshot is saved on your computer.
      4. Remote repository. You select Sync Changes. Your commit is pushed to GitHub, where others can see it.

      Why stage first? Staging lets you choose exactly what goes into each commit. You might have edited three files, but only two of them belong to the feature you are finishing.

      Common mistakes

      Forgetting to save

      Unsaved edits do not appear under Changes. Look for the dot on the editor tab and press Ctrl + S. You can turn on File > Auto Save.

      Committing without a message

      VS Code will not make a commit with an empty message. Always write a short, clear description of what the commit does.

      Forgetting to push

      Commits stay on your computer until you push. Check the status bar: if the up arrow shows a number, you have work to push.

      Not pulling before starting work

      If you work on more than one computer, or with others, always sync before you start. Otherwise you may edit an out-of-date copy and cause conflicts.

      Section 6 of 12

      Writing good commit messages

      Your commit history is a diary of your project. Clear messages make it easy to find changes later, and they show tutors and employers that you work in an organised, professional way.

      In this section you will

      • apply simple rules for writing commit messages;
      • tell the difference between a weak and a strong commit message.

      Key term

      A commit message is the short description saved with each commit. It should explain what the commit does and, where helpful, why.

      Seven simple rules

      1. Be specific. Say what changed: "Fix broken link to About page", not "Fix stuff".
      2. Use the imperative mood. Write it as an instruction: "Add", "Fix", "Remove", "Update". A good test: the message should complete the sentence "If applied, this commit will ...".
      3. Keep the summary short. Aim for 50 characters or fewer, so it is not cut off in lists.
      4. Start with a capital letter and do not end with a full stop.
      5. One logical change per commit. If you need "and" several times, split the work into separate commits.
      6. Add detail when it helps. After the summary, leave a blank line, then explain why the change was needed. In VS Code, press Enter for a new line in the message box.
      7. Never leave it empty or meaningless, such as "asdf" or "update".

      Worked example

      Examples of weak and improved commit messages
      Weak messageImproved messageWhy it is better
      fixed stuffFix broken link to About page in navigationSays exactly what was fixed and where.
      updateUpdate footer copyright year to 2026Someone can understand the change without opening the code.
      did loads of changes to css and html and jsThree commits: Add dark colour scheme, Add contact form markup, Validate email field in contact formEach change can be found, reviewed or undone separately.

      A message with extra detail looks like this:

      Fix contact form accepting an empty email address The form was submitted when the email field was blank, becausethe input had no required attribute. Add required and type="email".

        Section 7 of 12

        Branches in VS Code

        Branches let you work on a new feature without risking the version of your project that already works.

        In this section you will

        • explain what a branch is and why you should use one;
        • create and switch between branches in VS Code;
        • merge a branch back into main.

        Key terms

        Branch
        An independent line of development in a repository. Commits made on a branch do not affect other branches until you merge them.
        main
        The default branch in a new repository. It should always contain your latest working version.
        Merge
        To combine the commits from one branch into another, for example bringing a finished feature into main.

        Why use branches?

        Imagine you start adding a contact form, and halfway through, your tutor asks to see your working site. If you have been changing main directly, your site is half-finished. If you worked on a branch, main is untouched and still works.

        How to use branches in VS Code

        1. Create a branch. Select the branch name (for example main) at the bottom left of the status bar. Choose Create new branch..., type a name and press Enter. VS Code switches to the new branch straight away.
        2. Work as normal. Stage and commit in the Source Control panel. Your commits are added to the current branch only.
        3. Publish the branch. The first time, select Publish Branch to send the branch to GitHub. After that, use Sync Changes as usual.
        4. Switch branches. Select the branch name in the status bar and pick another branch from the list. VS Code updates your files to match that branch.
        5. Merge. Usually you merge on GitHub using a pull request (Section 8). You can also merge in VS Code: switch to main, open the Command Palette (Ctrl + Shift + P) and run Git: Merge....

        Naming branches

        Use lower case and hyphens, with no spaces, and describe the work: feature/contact-form, fix/nav-link, docs/readme-setup. Commit your work before switching branches, so nothing is carried across by accident.

        Predict first

        Your prediction

        The contact form was committed to feature/contact-form, so it does not exist on main yet. When you switch, VS Code changes the files in your folder to match the branch you are on. The work is safe on its branch and will appear on main once you merge.

        Section 8 of 12

        Pull requests on GitHub

        A pull request is how you propose merging a branch on GitHub. It gives you a chance to review your changes before they reach main.

        In this section you will

        • publish a branch from VS Code;
        • open, review and merge a pull request on GitHub;
        • bring the merged work back into VS Code.

        Key term

        A pull request (often shortened to PR) is a request, made on GitHub, to merge the changes from one branch into another. It shows every commit and changed line, and lets people comment and review before the merge happens.

        Do not confuse a pull request with pulling. Pulling downloads commits to your computer. A pull request is a GitHub page where you ask for a branch to be merged.

        Why use pull requests on your own projects?

        • The Files changed tab shows every line you changed, which helps you spot mistakes such as leftover test code.
        • Each pull request becomes a record of a completed feature, with a description of what you did and why.
        • In team projects and in industry, pull requests are the normal way to get code reviewed. Practising now prepares you for that.

          Section 9 of 12

          Resolving a merge conflict in VS Code

          Merge conflicts sound alarming, but they are a normal part of using Git. VS Code shows you exactly where the conflict is and gives you buttons to resolve it.

          In this section you will

          • explain why merge conflicts happen;
          • read conflict markers and identify the current and incoming changes;
          • resolve a conflict using VS Code and complete the merge.

          Key term

          A merge conflict happens when two branches have changed the same lines of the same file in different ways. Git cannot decide which version to keep, so it stops and asks you to choose.

          Worked example: two different headings

          On main, Sam changed the page heading to "Welcome to my portfolio". On the branch feature/about-page, Sam changed the same line to "Hi, I am Sam, a web developer". When Sam merges the branch into main, Git reports a conflict in index.html and adds conflict markers to the file:

          7<<<<<<< HEAD
          8 <h1>Welcome to my portfolio</h1>
          9=======
          10 <h1>Hi, I am Sam, a web developer</h1>
          11>>>>>>> feature/about-page
          • <<<<<<< HEAD starts the version from the branch you are on.
          • ======= separates the two versions.
          • >>>>>>> feature/about-page ends the version from the branch you are merging in.

          Predict first

          VS Code labels the two versions Current Change and Incoming Change. Sam is on main and is merging in feature/about-page. Which one is the Current Change?

          Your prediction

          Current is always the branch you are on (HEAD), which here is main. Incoming is the branch being merged in. It has nothing to do with which change was made most recently.

          Simulation: resolve the conflict

          Resolve the conflict using the options above the conflict, or open the merge editor. Then stage the file and commit to complete the merge. There is no single correct choice here: think about which heading suits the page.

          Simulation: merge conflict in index.html

          Tasks

          1. Resolve the conflict: choose Accept Current Change, Accept Incoming Change or Accept Both Changes, or use the merge editor and select Complete Merge.
            The buttons simply edit the file, removing the conflict markers and keeping the lines you chose.
          2. Stage index.html to mark the conflict as resolved.
            Staging a conflicted file tells Git you have resolved it.
          3. Commit to complete the merge.
            VS Code fills in a merge message for you. Committing finishes the merge.

            Avoiding conflicts

            Reduce the chance of conflicts

            • Pull before you start work every time.
            • Commit and push small changes often.
            • Keep branches short-lived: merge them within a few days.
            • In group work, agree who is editing which files.

            Common mistakes

            • Committing a file that still contains conflict markers. Search the file for <<<<<<< before staging.
            • Accepting both changes without tidying up, leaving duplicated code.
            • Panicking and deleting the repository. A conflict never loses work: both versions are in the file until you choose.

            Conflicts can also happen when you sync, if a commit on GitHub and your local commit changed the same lines. You resolve them in exactly the same way. GitHub also offers a Resolve conflicts button on pull requests for simple cases, but resolving in VS Code lets you test the result before committing.

            Section 10 of 12

            Using .gitignore and viewing history

            Some files should never be committed. A .gitignore file keeps them out of your repository. Your history, meanwhile, is always there to review in VS Code and on GitHub.

            In this section you will

            • decide which files should not be committed;
            • write a .gitignore file;
            • review commit history in VS Code and on GitHub.

            Key term

            A .gitignore file is a plain text file in the top folder of your repository. Each line is a pattern naming files or folders that Git should ignore. Ignored files never appear under Changes, so they cannot be committed by accident.

            What should be ignored?

            Types of file to ignore
            Type of fileExamplesWhy ignore it?
            Secrets and credentials.env, config.secret.jsonAnyone who can see the repository could use your passwords or API keys.
            Installed dependenciesnode_modules/, venv/Thousands of files that can be reinstalled with one command.
            Build outputdist/, bin/, obj/, __pycache__/Generated automatically from your source code.
            Logs and temporary files*.log, *.tmpChange constantly and are of no use to anyone else.
            Operating system files.DS_Store, Thumbs.dbCreated by macOS and Windows, not part of your project.

            Pattern rules: a plain name such as .env matches that file anywhere; a trailing slash such as node_modules/ matches a folder; an asterisk is a wildcard, so *.log matches every file ending in .log; lines starting with # are comments.

            Activity: write a .gitignore

            Sam's Source Control panel is full of files that should not be committed. Type patterns into the .gitignore file. The Changes list updates as you type. Ignore everything except Sam's own source files.

            .gitignore
            Source Control

            One pattern per line. You can also right-click a file in the real Source Control panel and choose Add to .gitignore.

            • .env holds secret keys.
            • node_modules/ is a folder of downloaded packages.
            • *.log matches all log files.
            • .DS_Store is created by macOS.

            Common mistake: uploading sensitive files

            Adding a file to .gitignore does not remove it if it has already been committed, and deleting it in a later commit still leaves it in the history, where anyone with access can find it. Automated bots scan public repositories for keys within minutes.

            How to avoid it: create your .gitignore before your first commit, and check the Changes list before every commit. If you have pushed a secret: treat it as compromised. Revoke or regenerate the key or password straight away, then remove the file and add it to .gitignore. Ask your tutor if you need help.

            Tip: when you create a repository on GitHub, choose a .gitignore template for your language (for example Node or Python) to start with sensible patterns.

            Viewing history

            Every commit is recorded permanently. You can review the history in both tools:

            In VS Code

            • The Graph section at the bottom of the Source Control panel lists recent commits for the whole repository. Select a commit to see the files it changed.
            • The Timeline section at the bottom of the Explorer panel shows the history of the file that is open in the editor.

            On GitHub

            • On the repository page, select the commits link (with a clock icon) above the file list.
            • Select any commit message to see exactly which lines changed. When viewing a file, the History button shows commits for that file only.
            git log lists commits. git show displays the details and changed lines of a single commit.

            Assessed projects

            • Check your assessment brief and your university's academic integrity policy before you start.
            • Keep the repository private unless the brief says otherwise. A public repository could be copied by others, and you may be asked to explain the similarity.
            • Add your tutor as a collaborator (Settings > Collaborators) only if the brief asks you to.
            • Commit regularly throughout. A steady history of meaningful commits is good evidence that the work is your own. One huge commit the night before the deadline is not.
            • Write a README.md explaining what the project does and how to run it.
            • Before the deadline, check on GitHub that your latest commit is there. Do not rely on work that is only on your computer.

            Personal and portfolio projects

            • Make finished projects public so employers can see them, but only once they contain no secrets.
            • Write a good README with a description, screenshots and setup instructions.
            • Pin your best repositories to your GitHub profile.
            • Add a licence if you are happy for others to reuse your code.
            • Keep using branches and pull requests: they show employers you understand professional workflows.
